## What this repo is

FlowSync is a training project (LIDR academy, AI4Devs cohort 202610-seniors-I). It is a TypeScript monorepo with two independent npm projects and no root `package.json`:

- `backend/` — AdonisJS 7 API (Lucid ORM on SQLite, VineJS validators, access-token auth). **Already complete; treat it as read-only** unless explicitly asked to change it. Read it to learn the real API contract.
- `frontend/` — React 19 + Vite 8 starter (still the Vite template). This is where feature work happens. The course expects shadcn/ui components (copied into the repo, not installed as a dependency).

`README.md` is generated from the course lesson ("no se edita a mano") — do not edit it. `prompts.md` is the student's prompt log for the exercise deliverable.

Requires **Node.js 24+** (backend runs `.ts` directly; Node 20 fails with `Unknown file extension ".ts"`).

## Commands

Backend (`cd backend`):

```bash
npm install
cp .env.example .env && node ace generate:key   # first time only
node ace migration:run                            # creates tmp/db.sqlite3 and regenerates database/schema.ts
npm run dev                                       # node ace serve --hmr → http://localhost:3333
npm test                                          # node ace test (Japa)
node ace test functional                          # one suite (unit | functional)
node ace test --files tests/functional/auth.spec.ts   # one file
node ace test --tests "test title"                # one test by title
npm run lint        # eslint
npm run typecheck   # tsc --noEmit
npm run format      # prettier (@adonisjs/prettier-config)
```

Test suites are declared in `backend/adonisrc.ts`: `tests/unit/**/*.spec.ts` and `tests/functional/**/*.spec.ts` (functional suite boots the HTTP server). No test files exist yet.

Frontend (`cd frontend`):

```bash
npm install
npm run dev      # vite → http://localhost:5173
npm run build    # tsc -b && vite build
npm run lint     # oxlint (.oxlintrc.json)
```

The frontend has no formatter and no test runner configured.

## Backend architecture

Request flow: `start/routes.ts` → controller (`app/controllers`) → `request.validateUsing(validator)` (`app/validators`) → Lucid model (`app/models`) → `ctx.serialize(Transformer.transform(model))` (`app/transformers`).

Key things that span multiple files:

- **Generated code — do not edit by hand.** `database/schema.ts` is regenerated by `node ace migration:run` (models extend `UserSchema` etc. from it). `.adonisjs/` (controllers index used as `controllers.X` in routes, Tuyau typed route registry, client types) is regenerated by the `indexEntities`/`generateRegistry` hooks in `adonisrc.ts` when the dev server/build runs. Schema changes go through a **new migration** in `database/migrations/`.
- **Response envelope.** `providers/api_provider.ts` adds `ctx.serialize()`, which wraps every payload in `{ "data": ... }`. Use `serialize.withoutWrapping()` to skip it. `force_json_response_middleware` makes all responses (errors included) JSON.
- **Transformers decide what leaves the server.** `UserTransformer` exposes `id, fullName, email, createdAt, updatedAt, initials`; `password` is never serialized.
- **Auth.** Default guard is `api` (opaque access tokens stored in `auth_access_tokens`, values prefixed `oat_`). Clients send `Authorization: Bearer <token>`. The `auth` named middleware protects routes; `silent_auth_middleware` runs on all routes.
- **Import aliases** via `package.json` `imports`: `#controllers/*`, `#models/*`, `#validators/*`, `#transformers/*`, `#middleware/*`, `#start/*`, `#config/*`, `#generated/*`, etc. Use them instead of relative paths.
- **CORS** allows any origin in development (`config/cors.ts`), with credentials.

### API contract (all under `/api/v1`)

| Method | Path | Auth | Body (from `app/validators/user.ts`) | Response `data` |
|---|---|---|---|---|
| POST | `/auth/signup` | – | `fullName` (string, nullable), `email` (email, ≤254, unique), `password` (8–32), **`passwordConfirmation`** (must equal `password`) | `{ user, token }` |
| POST | `/auth/login` | – | `email`, `password` | `{ user, token }` |
| GET | `/account/profile` | Bearer | – | `user` |
| POST | `/account/logout` | Bearer | – | `{ message }` (not wrapped) |

Note the signup validator requires `passwordConfirmation`, which product-level tickets usually omit — always check the validator before building a form. Validation failures come back as 422 with an `errors` array (field-level messages); bad login credentials come back as an error from `User.verifyCredentials`.

## Frontend notes

- Vite config is bare (`@vitejs/plugin-react` only): no path aliases, no dev proxy, no router, no HTTP client, no Tailwind/shadcn yet — any of these must be added deliberately.
- TS is strict-ish: `verbatimModuleSyntax` (use `import type`), `erasableSyntaxOnly` (no enums/namespaces/parameter properties), `noUnusedLocals/Parameters`.
- The backend package exports its generated types (`backend` → `./data`, `./registry`) for a typed Tuyau client if wanted.

## Process rules (harness)

Follow this workflow for feature work in this repository:

1. **Branch first.** Before editing application code, create/switch to a dedicated branch (never commit feature work directly on `main` or `s1/start`). Prefer names like `harness-<initials>` or a short ticket-based branch.
2. **Close the work with `/commit`.** When the change set is ready, stage deliberately and run `/commit` so the message is conventional (`tipo(scope): descripción`).
3. **Open the pull request** with `gh pr create` against the course upstream repo (not only the fork’s default), with a clear title/body.
4. **Adversarial review.** After the PR exists, invoke the `adversarial-reviewer` subagent on that pull request. It must try to break the change and must not edit files.
5. **Chat output.** When the PR is open, reply in chat with **only the pull request URL** (no long wrap-up essay unless the user asks).
