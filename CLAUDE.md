# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

FlowSync is a teaching project for an AI4Devs module on agent "harnessing" (LIDR academy). It's a
TypeScript-end-to-end monorepo: an AdonisJS 7 API backend and a React 19 + Vite frontend, split
into two independent, separately-installed projects under `backend/` and `frontend/`.

The backend (auth: signup/login/profile) is considered **done** and is not meant to be modified in
the current exercise — only read/explored. The frontend is a bare Vite+React scaffold where the
actual feature work (consuming the auth API) happens.

## Commands

### Backend (`backend/`, AdonisJS 7)

```bash
cd backend
npm install
cp .env.example .env
node ace generate:key      # populates APP_KEY in .env
node ace migration:run     # applies database/migrations/*.ts to the sqlite db
npm run dev                # node ace serve --hmr, http://localhost:3333
npm run build               # node ace build
npm test                    # node ace test (Japa)
npm run lint                 # eslint .
npm run format                # prettier --write .
npm run typecheck              # tsc --noEmit
```

Run a single test file: `node ace test tests/path/to/file.spec.ts`.

### Frontend (`frontend/`, React 19 + Vite)

```bash
cd frontend
npm install
npm run dev       # vite, http://localhost:5173
npm run build      # tsc -b && vite build
npm run lint         # oxlint
npm run preview       # vite preview
```

There is no test runner configured in the frontend yet. There is no formatter configured either
(no Prettier dependency) — `npm run lint` only runs oxlint.

Run backend and frontend in two separate terminals; the frontend expects the API at
`http://localhost:3333` (configure CORS_ORIGIN in `backend/.env` if needed, see
`backend/.env.example`).

## Architecture

### Backend: AdonisJS layering

Requests flow through named layers; when extending auth-related behavior, touch the matching layer
rather than improvising:

- **Routes** (`start/routes.ts`) — all API routes are under `/api/v1`, in two groups: `auth`
  (`POST auth/signup`, `POST auth/login`, unauthenticated) and `account`/`profile`
  (`GET account/profile`, `POST account/logout`, behind `middleware.auth()`).
- **Controllers** (`app/controllers/*.ts`) — thin; validate input via a validator, call the model,
  serialize via a transformer. See `access_tokens_controller.ts` (login/logout),
  `new_account_controller.ts` (signup), `profile_controller.ts`.
- **Validators** (`app/validators/user.ts`, VineJS) — `signupValidator` and `loginValidator` define
  exactly what the request body must contain (e.g. password min/max length, email uniqueness,
  `passwordConfirmation.sameAs('password')`). When a product ticket doesn't fully specify input
  shape, this is the source of truth.
- **Models** (`app/models/user.ts`, Lucid) — `User` composes the generated `UserSchema` with
  `withAuthFinder` for credential verification (`User.verifyCredentials`) and exposes
  `User.accessTokens` (a `DbAccessTokensProvider`) for issuing/revoking API tokens.
- **Transformers** (`app/transformers/user_transformer.ts`) — control exactly what's serialized to
  the client (e.g. `password` is excluded; `initials` is a computed getter that is included).
- **Migrations** (`database/migrations/*.ts`) — versioned schema changes; never edit the database
  by hand or edit an existing migration, always add a new one. `database/schema.ts` is
  **auto-generated** from migrations (regenerated by `node ace migration:run`) — never hand-edit it.

### Auth mechanism

Token-based (`tokensGuard`/`DbAccessTokensProvider`, see `config/auth.ts`), not sessions, despite
`@adonisjs/session` being installed (available but the `api` guard is the default). Tokens are
opaque strings prefixed `oat_`. Login returns `{ user, token }` where `token` is the bearer value
to send as `Authorization: Bearer <token>` on subsequent requests. Protected routes use
`middleware.auth()` (`app/middleware/auth_middleware.ts`), which reads `auth.getUserOrFail()` /
`auth.authenticateUsing()` in controllers.

### Path imports (backend)

The backend uses Node subpath imports (see `imports` in `backend/package.json`), not relative
paths: `#controllers/*`, `#models/*`, `#validators/*`, `#transformers/*`, `#middleware/*`,
`#database/*`, `#config/*`, `#start/*`, etc. all map into `app/`, `database/`, `config/`, `start/`.
Follow this convention for any new backend file rather than using relative imports.

### Frontend

Currently an unmodified Vite+React scaffold (`frontend/src/App.tsx`, `main.tsx`) with no routing,
state management, HTTP client, or UI library wired up yet, and no path aliases configured. The
onboarding materials (`README.md`) call for building login/signup/profile screens with shadcn/ui
against the three backend endpoints above; shadcn/ui components are meant to be copied into the
repo (not installed as an npm dependency), so expect a `src/components/ui/` directory to appear
once that's set up — it doesn't exist yet.

## Project-specific conventions

- TypeScript end-to-end, intentionally (pedagogical choice — see root `README.md` for rationale).
- Backend code is organized by Adonis convention (controllers/models/validators/transformers/
  migrations) — keep new backend code in the matching layer rather than collapsing logic into
  controllers.
- Don't hand-edit `backend/database/schema.ts` — it's generated.
- `backend/.env` and `backend/.env.test` are real (gitignored) env files, not just examples.

## Development workflow (Jira-backed harness)

Work on this repo is tracked in Jira, project **FLOW** (`iduetxe.atlassian.net`). Two skills
encode the expected flow end-to-end:

- **`/priority-ticket [FLOW-XXX]`** — picks a Jira ticket (the one given, or the highest-priority
  one in TODO if none is given), moves it to En progreso, assigns it to the current user, then
  reads the ticket and the relevant code and writes an implementation plan to
  `.claude/tmp/plans/FLOW-XXX-NombreTarea.md`. It asks any open business/product questions before
  writing the plan, never writes product code during planning, and waits for explicit plan
  approval (via Plan Mode) before implementing.
- **`/commit [FLOW-XXX]`** — creates a commit once a change is ready, formatted as
  `FLOW-XXXX :: Descripción breve del cambio`. It detects the ticket from the current branch name
  (or asks if it can't), drafts the short description from the staged diff, and asks for
  confirmation before staging files or pushing.

Commit message format for this repo (also enforced by `/commit`):

```
FLOW-XXXX :: Descripción breve del cambio
```

Keep the description short, imperative, and in the same language/tone as recent commits
(`git log --oneline`). See `.claude/skills/priority-ticket/SKILL.md` and
`.claude/skills/commit/SKILL.md` for the full step-by-step each skill follows.

## Reglas de proceso

Este es el ciclo completo que se sigue para cualquier cambio de código en este repo, de principio
a fin:

1. **Rama nueva antes de tocar código.** Nunca se commitea directamente sobre `main` ni sobre la
   rama en la que ya se está. Antes de editar cualquier archivo de producto — ya sea al arrancar
   `/priority-ticket` o al empezar a trabajar manualmente en un ticket — se crea una rama nueva
   desde la rama base actualizada, con el nombre:
   ```
   feature/FLOW-XXX-slug-corto-del-titulo
   ```
   usando el ID del ticket de Jira correspondiente. `/priority-ticket` crea esta rama
   automáticamente como parte de su flujo (ver `.claude/skills/priority-ticket/SKILL.md`).

2. **Cerrar el cambio con `/commit`.** Cuando el cambio está listo, se usa la skill `/commit`
   (`.claude/skills/commit/SKILL.md`) para crear el commit con el formato
   `FLOW-XXXX :: Descripción breve del cambio`.

3. **Abrir el pull request con `gh pr create`.** La descripción del PR debe explicar **qué** ha
   cambiado y **por qué** (la motivación / el ticket que lo origina), no solo listar archivos
   tocados. Enlaza el ticket de Jira (`FLOW-XXX`) en la descripción.

4. **Revisión adversarial del PR.** Tras crear el PR, se lanza el subagente
   `adversarial-reviewer` (`.claude/agents/adversarial-reviewer.md`) sobre ese PR. Es una revisión
   de solo lectura que intenta activamente encontrar fallos de seguridad, errores de ejecución y
   problemas de diseño/eficiencia — nunca edita código. Sus hallazgos se resumen al usuario, que
   decide si se corrigen antes de dar el ciclo por cerrado o se dejan para después.

5. **En el chat, solo la URL del PR.** Una vez creado el pull request, el mensaje final al
   usuario para cerrar el ciclo es la URL del PR — sin resúmenes largos ni repetir el contenido
   de la descripción ya escrita en el propio PR. (El resumen de hallazgos del paso 4 es aparte y
   antecede a este mensaje de cierre.)
